# 1.3 信頼性が高く回復性のあるアーキテクチャの設計(組織レベル)

## 試験で問われる観点

- RTO/RPO に基づく組織レベルの DR 戦略(詳細な DR パターンは [2-2](../02-new-solutions/2-2-business-continuity.md))
- 障害分離境界(AZ / リージョン / アカウント / パーティション)の使い分け
- サービスクォータ・API スロットリングを考慮した設計

## 障害分離境界 (Fault Isolation Boundaries)

| 境界 | 分離されるもの | 設計への示唆 |
|---|---|---|
| AZ | 電源・ネットワーク・物理設備 | マルチ AZ が基本。AZ 間は低レイテンシーの同期レプリケーション可 |
| リージョン | ほぼ全て(コントロールプレーン含む) | リージョン間は非同期が基本。DR・データ主権 |
| アカウント | IAM・クォータ・請求 | **ワークロード分離・爆発半径 (blast radius) の限定** |
| パーティション | aws / aws-cn / aws-us-gov | ARN も分離される |

- **コントロールプレーンとデータプレーン**: 障害時はデータプレーンの方が堅牢。「障害時に新規リソース作成(コントロールプレーン操作)に依存しない」= **静的安定性**。例: フェイルオーバー時に ASG のスケールに頼らず、事前にキャパシティを確保
- **セル型アーキテクチャ (cell-based)**: ワークロードを独立したセルに分割し、障害影響を一部顧客に限定。シャッフルシャーディングも同系統の考え方

## サービスクォータへの対応

- **Service Quotas** でクォータ確認・引き上げ申請。**クォータはアカウント×リージョン単位** → マルチアカウント分割はクォータ面でも有利
- API スロットリング(例: EC2 RunInstances)→ **エクスポネンシャルバックオフ + ジッター**、リクエストのキューイング
- DR 発動時にセカンダリリージョンのクォータが足りない事故 → **事前にクォータを両リージョンで揃える**(頻出の落とし穴)
- On-Demand Capacity Reservation / EC2 Fleet で DR 時のキャパシティを確保

## 組織レベルの回復性管理

- **AWS Resilience Hub**: アプリの RTO/RPO 目標に対する構成を継続評価、改善提案
- **AWS Fault Injection Service (FIS)**: カオスエンジニアリング(EC2 停止、AZ 障害シミュレーション等)
- **Route 53 ARC**: readiness check(両リージョンの構成・クォータの一致を監視)+ ルーティングコントロール
- AWS Health / Personal Health Dashboard + EventBridge で障害イベントを自動処理
- **Trusted Advisor の耐障害性チェック**(単一 AZ の RDS、バックアップ未設定等)

## マルチリージョンの組織的考慮

- データレジデンシー(域内保管)要件 → リージョン選定 + **SCP で利用リージョンを制限**(`aws:RequestedRegion` 条件)— 頻出
- グローバルサービスの例外: IAM, CloudFront, Route 53, WAF (CloudFront 用) は SCP のリージョン制限で除外が必要
- リージョン間のデータ複製手段は [2-2 のクロスリージョン複製表](../02-new-solutions/2-2-business-continuity.md) を参照

## 頻出のひっかけポイント

- 「特定リージョン以外の利用を禁止」→ SCP + `aws:RequestedRegion`(グローバルサービスの除外を忘れない)
- 「DR リージョンでインスタンスが起動できなかった」→ サービスクォータの事前引き上げ / キャパシティ予約
- アカウント分割は「セキュリティ境界」だけでなく「**クォータ・請求・爆発半径の分離**」でもある
- 「フェイルオーバーを確実に(DNS 制御が壊れても)」→ Route 53 ARC のルーティングコントロール(データプレーンは高可用)
