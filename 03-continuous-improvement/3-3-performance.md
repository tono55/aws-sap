# 3.3 パフォーマンスを改善する戦略

## このテーマの背景 — 「計測 → 特定 → 最小の一手」という規律

既存システムの性能改善が新規設計(2-5)と違うのは、**動いているものを壊さずに直す**制約が付くことです。問題文には「アプリケーションに変更を加えずに」「最小の変更で」という条件が高頻度で付き、この一言が選択肢の半分を消します(コード改修が必要な案はすべて落ちる)。

もうひとつの規律が「**計測が先、変更は後**」です。W-A のパフォーマンス効率の柱は「データに基づいて判断する」ことを求めます。「遅いからインスタンスを大きくする」は、ボトルネックが DB のロック待ちだったら1円の価値もない出費です。SAP でも「まだ原因が特定されていない」状況でいきなり構成変更する選択肢は、ほぼ確実に不正解として置かれています。まず観測ツール(X-Ray、Performance Insights、CloudWatch)で「どの層の・何が」遅いのかを突き止め、そこにだけ最小の一手を打つ — この診断プロセス自体が出題範囲です。

このノートは「診断の道具」→「層別の定番改善パターン」→「スケーリングの見直し」の順で、改善問題の解法を体系化します。

## 関連する Well-Architected の柱

- **パフォーマンス効率**: 「データに基づく選定」「メカニカルシンパシー」— 計測と、サービスの内部特性(レプリカの非同期性、キャッシュの整合性)を踏まえた改善
- **コスト最適化**: 性能改善とコスト削減が同じ一手になることは多い(gp3 化、ライトサイジング、キャッシュによる DB 縮小)
- **運用上の優秀性**: 観測基盤(3-1)の上にしか性能改善は成り立たない

## 診断 — どの層が遅いかを切り分ける

| 層 | ツール | 分かること |
|---|---|---|
| 分散システム全体 | **X-Ray** | サービスマップでどの区間(サービス間呼び出し)が遅いか |
| EC2 / コンテナ | CloudWatch メトリクス | CPU・メモリ(Agent)・ネットワーク・I/O の飽和 |
| DB | **RDS Performance Insights** | **待機イベントとトップ SQL** — 「DB が遅い」を「このクエリのこの待ち」まで分解 |
| ストレージ | CloudWatch(IOPS/スループット/キュー深度) | EBS の上限到達、バースト残高の枯渇 |
| フロントエンド | CloudWatch RUM / Synthetics | 実ユーザー体感・外形での応答時間 |
| コスト対性能 | **Compute Optimizer** | ML ベースの過剰/過小プロビジョニング判定 |

```mermaid
flowchart TD
    START(["「遅い」という報告"]) --> Q1["X-Ray サービスマップで<br>どの区間が遅いか特定"]
    Q1 -->|"DB 呼び出しが遅い"| DB["RDS Performance Insights<br>(待機イベント・トップ SQL)"]
    Q1 -->|"アプリ処理が遅い"| APP["CloudWatch メトリクス<br>(CPU / メモリ / 同時実行)"]
    Q1 -->|"外部 API / ネットワーク"| NET["VPC Flow Logs /<br>リージョン間レイテンシー確認"]
    Q1 -->|"ユーザー側の体感のみ"| FE["CloudWatch RUM / Synthetics<br>(エッジ配信・CloudFront 検討)"]
    DB --> FIX1["インデックス / リードレプリカ /<br>キャッシュ導入"]
    APP --> FIX2["ライトサイジング / スケール /<br>非同期化"]
```

診断ツールの選択自体が設問になります。「マイクロサービスのどこが遅いか」= X-Ray。「DB のどのクエリが重いか」= Performance Insights。「ユーザー体感は悪いがサーバーは正常」= RUM/Synthetics(→ 配信経路の問題を疑い CloudFront へ)。

## 層別の定番改善パターン — 「現状の記述」から「一手」へ

改善問題は「現状の構成と症状」→「最適な一手」の対応付けです。頻出パターンを症状から引けるように整理します。

### データベース層

| 症状 | 一手 | 理由 |
|---|---|---|
| 読み取り負荷でプライマリが飽和 | **リードレプリカ**+読み書き分離 | 読みは複製で水平スケールできる。Aurora ならリーダーエンドポイントで振り分けも自動 |
| 同じクエリが何度も実行される | **ElastiCache**(結果キャッシュ) | 繰り返しをメモリで吸収し DB への到達自体を減らす |
| DynamoDB の読みが遅い/高い | **DAX** | API 互換でコード変更最小のまま マイクロ秒化(2-5 参照) |
| Lambda からの接続でコネクション枯渇 | **RDS Proxy** | 大量の短命接続をプールで束ねる |
| 書き込みスパイクで DB が倒れる | **SQS を挟んで平準化** | 書き込みは非同期化でピークを均す(2-4 の疎結合) |
| 分析クエリが本番 DB を圧迫 | リードレプリカで分離 / **zero-ETL + Redshift** | OLTP と OLAP の分離(適材適所) |

### コンピューティング/アプリ層

| 症状 | 一手 | 理由 |
|---|---|---|
| Lambda の初回応答が遅い | **プロビジョンド同時実行** / SnapStart (Java) | コールドスタート(初期化)を事前に済ませる |
| 重い同期処理で応答が遅い(画像処理等) | **SQS + ワーカーで非同期化** | 応答と処理を分離し、体感を即時にする |
| ASG のスケールが需要に追いつかない | **ウォームプール / 予測スケーリング / golden AMI** | 起動時間の短縮と先読み。user data の長い初期化は AMI に焼き込む |
| CPU は余っているのに遅い(ネットワーク律速) | インスタンスサイズ/ENA/プレイスメントグループ | 帯域はサイズに比例。同一ラック配置でレイテンシー削減 |

### ストレージ/配信層

| 症状 | 一手 | 理由 |
|---|---|---|
| EBS の IOPS 不足(gp2) | **gp3 化して IOPS を独立設定** | gp2 はサイズ比例でしか性能が出ない。gp3 は安くて独立設定可 |
| ALB 経由で静的コンテンツを配信している | **CloudFront + S3 にオフロード** | 静的物にコンピューティングを使わない。エッジで返す |
| 遠隔地からの S3 アップロードが遅い | **Transfer Acceleration** + マルチパート | エッジ経由で AWS 網に早く乗せ、並列化する |
| Athena が遅い・高い | **Parquet 化 + パーティション + 圧縮** | スキャン量を減らすことが速度とコストの両方に効く |
| Redshift の同時実行待ち | Concurrency Scaling / WLM 調整 | ピーク時だけクラスタを自動増設 |

パターン暗記に見えますが、背後の原理は 2-5 と同じ3つ(近くへ・繰り返さない・適材適所)+「非同期化」です。新しい症状に出会ったら原理に戻って導出してください。

## スケーリングと「作り直さない」改善の限界

改善ドメインでは「インフラの一手」で解ける問題が中心ですが、限界も問われます。リードレプリカは**非同期**なので、直後の読み取りに最新値が必要な処理(残高表示など)はプライマリに向けるか設計の見直しが必要です。ElastiCache の導入には**整合性の設計**(Lazy Loading の stale 許容か、Write-Through の書き込みコスト負担か、TTL はいくつか)が伴います。DynamoDB のホットパーティションは、容量をいくら足しても**キー設計を直さない限り**解消しません。「インフラで吸収できる問題」と「設計に踏み込むべき問題」の境界を見極める記述が、上位問題の差別化ポイントです。

## ケーススタディ

**シナリオ**: 月次レポート画面が遅いと苦情。構成は ALB + EC2 + RDS MySQL。調査の結果、Performance Insights で特定の集計 SQL が全実行時間の 8 割を占め、同じパラメータで1日に数千回実行されていた。アプリ改修は最小限にしたい。改善は?

**解き方**: 計測済み(Performance Insights)で原因は「同一クエリの反復」。原理は「繰り返さない」— **ElastiCache** で結果をキャッシュし TTL を業務要件(月次データなら長め)に合わせる。レプリカ追加は反復自体を消せないので次点、インスタンスのスケールアップは原因(クエリ反復)に対して的外れ。「アプリ改修最小限」との兼ね合いでは、キャッシュ層の追加は読み取りパスの限定的な変更で収まる点を評価する。

**シナリオ**: グローバル SaaS。欧州ユーザーから「アジアのユーザーより明らかに遅い」と苦情。サーバーは東京リージョンの ALB + ECS。CloudWatch 上のバックエンド処理時間は正常。

**解き方**: サーバー正常+地理差 = **ネットワーク距離の問題**。静的アセットと API の両方を **CloudFront** 経由に(動的 API でも接続最適化・TLS 終端のエッジ化で改善)。さらなる要件(数十 ms 級)なら欧州リージョン追加 + Route 53 レイテンシールーティング(ただしデータ層のレプリケーション設計が伴うため「最小の変更」なら CloudFront が先)。ECS のスケールアウトはバックエンドが正常な時点で的外れ。

## 試験直前の要点(理由つき)

- **「原因未特定でスケールアップ」は不正解の型** — 計測(X-Ray / Performance Insights)が先。データに基づく判断が柱の原則
- **「アプリ変更なし」の制約で選べる道具を覚える** — gp3 化・リードレプリカ・RDS Proxy・DAX・CloudFront・Transfer Acceleration はインフラ側だけで効く
- **リードレプリカは非同期** — ラグがある。「直後に最新を読む」要件には使えない、が定番の追加条件
- **Lazy Loading vs Write-Through** — 前者は初回ミスと stale、後者は書き込みコストと引き換えの常時新鮮。TTL 併用が実務解
- **DynamoDB のスロットリングは容量でなくキー設計** — ホットパーティションは物理分散の偏りだから
- **gp2 → gp3 は性能とコストの同時改善** — 「サイズ比例」から「独立設定」への転換が本質
- **golden AMI = 初期化を起動前に済ませる** — スケール速度問題の定番解。ウォームプールと同じ発想
- **静的コンテンツを ALB/EC2 から配るのはアンチパターン** — CloudFront + S3 へのオフロードで性能とコストが同時に改善
